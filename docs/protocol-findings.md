# MHT-500 protocol findings

Research and static analysis: 7 October 2026. Target: Android phone/tablet running Chrome.


## What is established

The [manufacturer’s MHT-500 specification](https://www.milestoneiot.com/v1/products/A4receiptprinter_1878_45.html) lists Bluetooth 4.2 and USB, 8 dots/mm, 1728 dots per line, and a 210/216 mm effective width. It calls the printing command set **ESC**, which by itself does not document a complete ESC/POS implementation. It does not list Wi-Fi.

The actual transfer path was reconstructed by statically inspecting the manufacturer’s [TattooPrinter Android app](https://www.mhtclouding.com/tattooprint/download.html). No APK was installed or executed. The downloaded app is package `com.mht.tattooprint`, version **2.0.9.4**, versionCode **153**. The inspected APK has SHA-256:

`82c8db3456d2b560ca202b0029a8714073c2b056f6a6c4d9f7640a80bb799c95`

This is substantially stronger evidence than a generic ESC/POS guess, but **it has not yet been tested against the user’s physical printer**. The exact label, advertised device name, firmware version, and current printing app remain to be confirmed.

## Bluetooth transport

The print preview’s active connection implementation opens an Android Bluetooth Classic RFCOMM socket using the Serial Port Profile service:

`00001101-0000-1000-8000-00805f9b34fb`

The implementation uses `createRfcommSocketToServiceRecord`, then the socket’s input and output streams. The normal print path is not a BLE/GATT characteristic write. No BLE service UUID is required for this path. Device names explicitly include MHT-500, GT-500, F200 and IMP-216 in the relevant MHT-500 family list; these aliases are not a guarantee that every rebranded unit behaves identically.

The app writes data in **4096-byte blocks**, flushes each block, and waits **100 ms** after each full block. A remaining partial block is written without that delay. These are transport pacing boundaries, not packet headers: they may split raster rows.

Static evidence: `pj/e.java`, service constant around line 83, socket setup around 254, and send method around 491; `PrintPreviewActivity.java`, connection field around 118.

## Queries that do not print

The app uses `10 04 n` for device information:

| Request | Hex bytes |
|---|---|
| Paper status | `10 04 04` |
| Device model | `10 04 06` |
| Firmware version | `10 04 08` |
| Battery/power | `10 04 09` |
| All information | `10 04 0A` |

The application has several response parsers, including JSON with `ver`, `paper`, and `bat` fields and responses with an initial `02` byte. A complete response format for the user’s unit still needs a captured response; do not assume each Bluetooth read yields an entire message. The pilot accumulates received data and preserves its hex and text for inspection.

Static evidence: `DeviceInfoEnum.java`; `oj/j.java`, method `y`; `HomeActivity.java`, response handling around 600.

## Normal uncompressed MHT-500 image format

The model-specific normal path ends up in `oj/j.java`, methods `x0` and `n0`, with settings generated by `oj/f.java`, method `m`. This is a proprietary row format, not the generic `GS v 0` raster command.

Each monochrome row is:

```text
16 N [N bytes of raster data] 15 01
```

- `16`: row marker.
- `N`: unsigned one-byte row width, in **bytes** (not dots or millimeters).
- Raster pixels run left to right, eight pixels per byte, **most significant bit first**. Bit 1 means a black/heated dot; bit 0 means white.
- `15 01`: row advance as used by the app.
- Rows run from top to bottom.

At 210 mm and 8 dots/mm, a row has 1680 dots and 210 raster bytes: `16 D2 … 15 01`. A full 1728-dot row would have 216 raster bytes (`D8`), but the app’s normal/default MHT-500 path does not automatically use the full nominal head width.

The official app rasterizes its image using grayscale/dithering before bit packing. Our calibration pattern is already binary, so it avoids differences in image preprocessing while testing the transport, row framing and physical scale. Later stencil rendering can use our own threshold/dithering controls without reproducing the official editor.

## Setup sequence and firmware differences

The setup begins with `1B 40`, followed by six five-byte settings commands of the form:

`1F FD 01 setting value`

The numeric settings are identified from the application’s code; their internal hardware semantics are not fully documented. Preserve the recovered combinations instead of guessing values.

| Setting | Older MHT-500 firmware | Firmware dated August 2026 or later |
|---|---|---|
| `01` | `10` | `08` |
| `02` | `64` | `64` |
| `03` | `01` | `01` |
| `04` | `02` | `04` |
| `05` | `00` | `00` |
| `06`, low density | `82` (130) | `64` (100) |
| `06`, normal density | `A0` (160) | `78` (120) |
| `06`, thick density | `BE` (190) | `96` (150) |
| Normal raster width | 210 mm / 1680 dots | 208 mm / 1664 dots |

Example older-firmware **normal-density** setup:

```text
1B 40
1F FD 01 01 10
1F FD 01 02 64
1F FD 01 03 01
1F FD 01 04 02
1F FD 01 05 00
1F FD 01 06 A0
```

The newer combination is selected by the app’s MHT-500 family check and a firmware year/month comparison against `202608`. Its date extraction reads the six characters after the last `H`. Earlier firmware capability checks also use `PM500203H2024111601`; that threshold is distinct from the August 2026 width/settings change. A version in a different naming format should be inspected instead of silently assigned a profile.

Static evidence: `lk/f.java`, MHT-500 family `q`; `HomeActivity.java`, around 247–253; `lk/h.java`, methods `c` and `d`; `oj/j.java`, `Y`, `Z`, and `x0`; `oj/f.java`, `S()` branch.

## Complete normal job

```text
[setup bytes for the correct firmware and density]
[row 0: 16 N raster... 15 01]
[row 1: 16 N raster... 15 01]
...
0A 0A 0A
1F 01 06
```

The last three bytes are the official app’s end marker. The MHT-500 model does not enter the additional four/six-line leading-feed branches in this normal path. Bluetooth pairing happens separately; there is no additional authentication exchange evident in this ordinary unencrypted print path.

The broader app also contains compressed and encrypted print paths for other models and optional settings. Finding those branches does not establish that the MHT-500 needs them. The default settings model sets encrypted printing false; this investigation reconstructs the ordinary MHT-500 path, not every firmware feature or optional mode.

## Browser feasibility

**A browser app is a realistic option on the requested Android device.** [Chrome 138’s official release notes](https://developer.chrome.com/release-notes/138) introduced Web Serial over Bluetooth RFCOMM on Android. [Chrome’s Bluetooth serial documentation](https://developer.chrome.com/blog/serial-over-bluetooth) also describes paired Bluetooth Classic services and SPP on desktop Chrome.

The site must run in a secure context (HTTPS), request the connection from a user gesture, and be opened directly in a supported browser. The printer must be paired with Android first; settings do not have to show an active connection. Pairing may already have been completed by TattooPrinter. Its native path handles both bonded and unbonded devices in `pj/e.java` method `v`, then opens the RFCOMM socket in method `t` and connects in method `H`. Android can [initiate pairing during that native connection](https://developer.android.com/develop/connectivity/bluetooth/connect-bluetooth-devices). The website cannot perform the same native discovery and pairing sequence; once the printer is paired, a page can request the SPP service and send binary data through Web Serial. A local helper is unnecessary **if the user’s device exposes the printer’s SPP service correctly**. That last condition needs a real connection test.

Wi-Fi/mobile data can load and update the website; the print job travels directly from the browser to the nearby printer over Bluetooth. No cloud server needs to contact the printer. Installing an icon on the home screen would not add missing Bluetooth APIs to an unsupported browser.

## First pilot and validation

The private **Stencil Link** pilot supports connecting, reading model/firmware information, selecting the recovered settings, and sending a small calibration pattern. It requires a model confirmation and a selected firmware profile before printing. It has no firmware-update commands and no automatic printing. Its report includes the browser version, firmware/profile, received bytes, transfer result and the user’s physical-print result; it is copied manually, not uploaded automatically.

The pattern’s rectangle has outer dimensions of 320 × 160 dots, corresponding to 40 × 20 mm at 8 dots/mm. The full calibration raster is 256 rows high. Older-firmware job length: 54,822 bytes; newer-firmware job length: 54,310 bytes, including setup and completion bytes. The pilot uses the recovered low-density setting.

Verification completed: JavaScript syntax, independent setup-byte vectors, raster bit order and row framing, invalid-dimension rejection, firmware boundary selection, and complete calibration-job lengths. A simulated browser flow also passed split-response assembly, model/profile gates, full calibration transmission and stream-lock cleanup. The browser connection and physical print remain unverified until the user tests the actual printer. WebMCP report access is feature-detected; validation in a supported live WebMCP browser context was unavailable.

To proceed, open the pilot in current Android Chrome, pair the printer, close TattooPrinter, connect, and read information. Copy the report back into the chat. Also confirm the model on the physical label and the app you use. After the calibration succeeds, the same connection layer can support a browser stencil editor with exact millimeter sizing, rotation, mirroring and canvas placement.
